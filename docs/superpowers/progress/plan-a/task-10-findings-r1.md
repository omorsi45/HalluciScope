# Task 10 open findings (round 1), verbatim from the review, with controller rulings

1. (Spec and Important) The unhandled-error 500 lacks the security and CORS headers, and the comment says otherwise (backend/api/middleware.py:55-58). The 500 is emitted from the outermost RequestContext middleware after the exception has propagated out of SecurityHeaders and CORS. Probe: GET /api/v1/_boom with a listed Origin returned 500 with X-Request-ID but no nosniff, no CSP, no Access-Control-Allow-Origin; a 404 had them all. The SPA cannot read the 500 body or request id cross-origin. Test only checks x-request-id (tests/test_api_skeleton.py:88). Fix: produce the 500 inside CORS (catch in the innermost middleware, for example a small ServerErrorMiddleware-like wrapper added innermost, keeping RequestContext's catch as a fallback); extend the test with an Origin header asserting nosniff and access-control-allow-origin.
2. (Important) method metric label has unbounded cardinality (backend/api/middleware.py:63-65). scope["method"] is client-controlled; h11 accepts any token; the registry creates a child per label tuple. Probe: 50 methods created 50 http_requests_total series. Fix: map to GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS, else OTHER.

Controller rulings for the same round (cheap, same lines, security relevant):
- Request id validation uses re.fullmatch (rejects a trailing newline); add a test case.
- Content-Length parsing accepts only ASCII digits and at most 19 characters; anything else is treated as absent (streamed counting still applies); add a test case with "\u00b2" via a raw ASGI scope.
- create_app raises ValueError when "*" is in settings.cors_origins (credentialed wildcard is the bug this project removes); add a test.
- startup.py lifespan: wrap startup after db.open() in try/except that closes the pool on failure, and close each resource in its own try/finally on shutdown; correct the uvicorn docstring to name the concrete invocation: programmatic `uvicorn.run(..., log_config=None)`, CLI `uvicorn ... --log-config /dev/null` is NOT valid, so the documented CLI form is to rely on configure_logging inside the lifespan, which runs after uvicorn configures logging and replaces its handlers (state exactly what configure_logging does to the uvicorn and uvicorn.access loggers).
