# Task 8 open findings (round 1), verbatim from the review

1. backend/auth/passwords.py:65-69. The bound is memory-only, so a stored hash can make verify burn CPU for hours. The worst parser-accepted, OpenSSL-valid case is `scrypt$131072$2$131070$...` (n*r*p is 262,140 times the default), which extrapolates to about 3.7 CPU-hours per verify_password call. Fix: bound total work, for example `n * r * p <= _N * _R * _P * 16`, or cap p (p <= 16). Add a test asserting scrypt is never called for such a hash.
2. tests/test_passwords.py:69 and the strict-parse tests (lines 60-78, 89-101). Most cases pass only because the digest mismatches, not because the parser rejects them. Evidence: the padded case `c2FsdA==`, labeled "padded base64 is not our encoding", is accepted by `_parse_stored`. A correctly padded variant of a valid hash makes `verify_password` return True, and so does a single appended `=`. Every case in test_unsafe_scrypt_parameters_are_false would also return False through hashlib's own ValueError if the guards were deleted. Fix: mutate a hash that otherwise verifies (built with `_stored(...)`) and assert False, or assert scrypt is not called. Controller ruling: reject `=` in `_decode` (our format is unpadded only), and require the decoded digest to be exactly 32 bytes and the salt exactly 16 bytes (the format has no dklen field; dklen is the digest length, and we only produce 32).
